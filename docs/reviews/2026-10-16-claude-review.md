# Повторное ревью через консольный Claude — 16 октября 2026

> Исторический отчёт по 1.6.1. Исправления и новое ревью: [результат 1.6.2](2026-10-16-claude-fixes-review.md).

Проверена версия **1.6.1, commit b66e294**. Ревью действительно выполнено через установленный
**Claude Code CLI 2.1.301**, затем ему переданы результаты проверки на эмуляторе,
ответ пользователя и возражения к первоначальным выводам. Claude работал только с Read/Glob/Grep;
код не редактировал и тесты не запускал. Его выводы ниже сверены с исходниками и отдельными пробами.

[Полный исходный ответ Claude и его последующие поправки](2026-10-16-claude-transcript.md).
Первоначальная оценка P0 и предложение автоматически переключать компонент сервиса
**не приняты**; Claude отозвал эту рекомендацию после уточнений. Подтверждённых P0 нет.

## Главное

1. **P1: парсер может отправить неверную сумму.** `BankNotificationParser.kt:60–68` принимает число сразу
   после слова операции без валюты. Поэтому время `14:05` может стать суммой `14`, хотя в сообщении
   дальше есть `500р`. Результат воспроизведён на скомпилированном коде текущей версии.
2. **P2: часть формулировок поступления пропускается.** `BankNotificationParser.kt:33` отклоняет
   исходящие слова в любой части текста, включая «Вам отправлен перевод» и комментарий отправителя.
   Регулярное выражение числа также объединяет соседний номер карты с суммой, после чего весь разбор
   завершается с null (`:20,51–68`). Эти результаты воспроизведены; частота таких форматов у конкретных
   банков не измерялась, обезличенного корпуса реальных сообщений пока нет.
3. **P1: отсутствует понятная помощь при зависшем подключении слушателя.** Доступ может числиться
   выданным, а callback подключения не приходить. Повторение requestRebind не гарантирует новую
   привязку. На POCO пользователя помогла повторная выдача доступа. Нужны различимые состояния
   «нет доступа», «ожидаем подключения», «система долго не подключает» и переход к настройкам доступа.
   Это не доказательство дефекта SDK, manifest или всех Android-устройств.
4. **P2: после исправления настроек очередь может продолжать ждать старый backoff.**
   `DeliveryQueue.kt:38–41`, `OutboxDelivery.kt:13`, Save/Test/import не ускоряют уже отложенную работу
   с KEEP. Экспоненциальная задержка до 5 часов документирована и сама по себе не регрессия;
   полезно отдельно спроектировать ускорение после восстановления, сохранив retry_after Telegram.
5. **P2: неверная конфигурация прокси принимается без понятного объяснения.**
   SOCKS-аутентификация явно не поддерживается в README, но URI с логином/паролем сохраняется;
   HTTP proxyAuthenticator не реализует SOCKS-аутентификацию. Нужна проверка при сохранении
   и указание строки с ошибкой вместо общего сообщения «Ошибка сети».

Ошибки парсера выше **не исправлены этим проходом ревью** и остаются в 1.6.1.
В репозитории изменены только отчёты и неточные описания текущего поведения.

## Выполненные проверки

На текущих скомпилированных классах через JDK 25/jshell получены результаты:

| Вход | Фактический результат | Ожидание для такого текста |
|---|---|---|
| `Зачисление 14:05 500р` | `14` | `500`, время не должно быть суммой |
| `Пополнение MIR-2923 500р` | `null` | `500` |
| `Зачисление на счёт *1234 500 ₽` | `null` | `500` |
| `Вам отправлен перевод 500 ₽` | `null` | `500` |
| `Перевод 500 ₽ от Иван И. Сообщение: отправлено получателю` | `null` | `500`, комментарий не должен менять направление операции |
| `Зачисление 500 ₽` | `500` | `500` — контрольный пример |

Это проверка воспроизводимости на синтетических строках, а не доказательство того,
что конкретный банк присылает именно эти шаблоны. Исправления должны сопровождаться
регрессионными тестами и примерами реальных сообщений без персональных данных.
## Проверка сбоя слушателя после обновления

- Сообщение пользователя: POCO F6 Pro с последним обновлением; 1.6.0 работала, после установки 1.6.1 в журнале только «Запрошено переподключение к системе».
- Пользователь подтвердил восстановление после отключения и повторной выдачи доступа к уведомлениям. Точная версия Android/HyperOS и системный logcat телефона не получены, поэтому конкретная причина внутри прошивки не установлена.
- В изолированном Android 14 (API 34) эмуляторе установлена опубликованная signed 1.6.0, выдан доступ, затем установлен signed GitLab APK 1.6.1 с `adb install -r`, без удаления данных. Обе версии получили `onListenerConnected`; обновление переподключилось без повторной выдачи разрешения.
- Проверено также `am force-stop` → открытие 1.6.1: сервис повторно подключился. Это подтверждает работоспособность проверенного сценария на AOSP, но не воспроизводит HyperOS.
- Manifest готового APK содержит прежний компонент `com.banknotify.BankNotificationListener`, exported=true и BIND_NOTIFICATION_LISTENER_SERVICE. ListenerRecovery/ListenerReconnectLoop между 1.6.0 и 1.6.1 не изменялись.
- Android `requestRebind` — запрос, а не подтверждение подключения. В AOSP `ManagedServices.setComponentState` может завершиться без новой привязки, если внутреннее enabled-состояние уже совпадает. Подтверждение приложения — только callback `onListenerConnected`.

Источники: [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [ManagedServices Android 14](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/core/java/com/android/server/notification/ManagedServices.java).

Практическое улучшение: при длительном отсутствии callback явно показывать «Доступ выдан, система ещё не подключила сервис» и инструкцию повторного включения доступа; не выдавать успешный requestRebind за успешное подключение. Автоматическое переключение PackageManager component enabled-state требует отдельной проверки сохранения системного разрешения; без неё такой обход не внедрялся.

## Остальные замечания и ограничения

- Журнал живёт только в памяти процесса; после его смерти нельзя восстановить историю подключения.
  Для диагностики полезен ограниченный файл в noBackupFilesDir с PID/временем запуска и причиной
  завершения процесса через ApplicationExitInfo. Токены, пароли и сырой текст уведомлений туда попадать не должны.
- Инициализация EncryptedSharedPreferences/Keystore из Application и UI может выбросить исключение;
  общего безопасного сценария такой ошибки нет. Нельзя «исправлять» это безусловным удалением prefs/ключа:
  это потеряет настройки. Нужна обработка с сохранением исходных данных и понятным состоянием ошибки.
- Новая таблица telegram_outbox получает сообщения; старая bank_notifications в production больше
  не пополняется. Старые записи остаются в базе. Утверждение первого отчёта о сохранении сырого
  текста в истории было неверным; в outbox сохраняется отформатированная строка.
- Сертификат release проверен вручную для локального и опубликованного GitLab APK, но CI пока
  не сравнивает отпечаток с закреплённым ожидаемым значением. Стоит добавить такой барьер.
- Новый OkHttpClient создаётся для каждой попытки, отправленные строки outbox не чистятся,
  есть неиспользуемые экраны/параметры DAO и повторное добавление TextWatcher в AppPickerDialog.
  Это последующие улучшения, а не подтверждение текущей потери оплат.
- В диагностике полезно показать последнюю ошибку доставки без добавления отвергнутого пользователем
  экрана очереди. Постоянные ошибки Telegram сейчас повторяются по принятой политике, пока настройки не исправлены.
- Системное переподключение, планирование WorkManager и настоящий HTTP/SOCKS маршрут покрыты
  заметно слабее, чем чистые функции парсера. Нужны интеграционные сценарии, включая минифицированный APK.
- В этом проходе проверен реальный Android API 34 emulator. API 35/37 и повторное обновление
  на HyperOS не проверены; пользователь подтвердил только восстановление повторной выдачей доступа.

## Какие рекомендации Claude не следует применять буквально

- **Не переключать автоматически PackageManager component enabled-state без отдельной проверки.**
  Не доказано, что это сохраняет разрешение и работает одинаково на OEM-прошивках.
- **Не объединять одинаковый текст на 10 минут и не считать notification.when идентификатором платежа.**
  Можно потерять две реальные одинаковые оплаты при повторном использовании банком notification ID/времени.
  Текущий выбор в пользу возможного дубля сохраняется. Безопасное объединение требует идентификатора операции.
- **Не считать снимок WorkInfo.state защитой от гонки при REPLACE.** Пока выполняется проверка,
  ENQUEUED может стать RUNNING. Перепланирование нужно проектировать и проверять как отдельный механизм;
  retry_after Telegram нельзя обнулять просто из-за успешного Test.
- **Не считать длинный backoff и отсутствие SOCKS-аутентификации новыми регрессиями.**
  Они описаны в README; проблемы — в обратной связи и восстановлении после изменения настроек.
- **Не выводить точную причину сбоя POCO из одной строки журнала.** Сохранённое разрешение,
  вызов requestRebind и реальное подключение — разные состояния. Успешная повторная выдача доступа
  подтверждает обходной путь, но без системных логов не доказывает внутренний дефект HyperOS или targetSdk.
